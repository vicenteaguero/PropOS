# PropOS API Reference

45 routers, 219 routes. Generated by walking `app.routes` on the built
application and reading each route's dependency tree, so the gates below are the
ones FastAPI actually evaluates — not a summary written from memory.

Re-derive it after changing a router: `backend/app/main.py` mounts everything,
and in any non-production environment the live spec is at `/openapi.json` with a
browsable UI at `/docs` (both are disabled when `APP_ENV=production`,
`main.py:164-166`).

## Base URL

Every feature route is mounted under `/api/v1`
(`API_PREFIX="/api"` + `API_VERSION="v1"`, `backend/app/core/config/constants.py:1-2`,
joined at `backend/app/main.py:179`). There is no unversioned `/api` surface.

Four routes sit outside the versioned prefix:

| Path | Purpose |
|---|---|
| `GET /health` | Liveness. Static `{"status":"healthy"}`, touches nothing. |
| `GET /health/ready` | Readiness. Probes the DB and core secrets; **503** when either fails. |
| `GET /r/{slug}`, `POST /r/{slug}/verify-password` | Public document share links. |
| `GET /p/{slug}`, `POST /p/{slug}/upload` | Public anonymous upload portals. |

The share/portal routes are mounted with no prefix at all
(`main.py:223`, `documents/router.py:372-500`) because the slugs are pasted into
WhatsApp and email; they are deliberately short and deliberately unversioned.

## Authentication

Three different mechanisms are in play. Which one applies depends on the route,
and they are not interchangeable.

**1. Supabase JWT — 208 of the 219 routes.**

```
Authorization: Bearer <supabase-jwt>
X-Tenant-Id: <uuid>          # optional; selects the active tenant
```

`get_current_user` (`backend/app/core/dependencies.py:19-46`) verifies the token
against Supabase, loads `profiles` merged with the active `tenant_memberships`
row, and returns `{id, role, tenant_id, full_name, admin_scope, is_dev_admin, view}`.
A bad token or a missing profile is **401** `{"detail": "Invalid or expired token"}`.

`X-Tenant-Id` is read by `get_tenant_id` → `resolve_active_tenant`
(`backend/app/core/tenant.py`). It must be a UUID (**400** otherwise) and the
caller must hold an active membership in it (**403** otherwise). Omit it and the
user's current tenant snapshot is used, falling back to their first active
membership.

**2. Shared secret header — the internal cron routes.**

```
X-Internal-Key: <INTERNAL_JOBS_SECRET>
```

`backend/app/features/jobs/router.py:17-25`. No JWT, no tenant. A wrong key is
**403**; an unset `INTERNAL_JOBS_SECRET` disables the endpoints with **503**, which
is their state in production today (see `docs/cron-jobs.md`). The same header
also unlocks the `detail` block of `/health/ready` outside development
(`main.py:275-279`).

**3. HMAC-SHA256 — the Kapso webhook.**

```
X-Webhook-Signature: <hmac-sha256 of the raw body, keyed by KAPSO_WEBHOOK_SECRET>
```

`backend/app/features/integrations/kapso/webhook.py:28-41`. Verified over the raw
request body before anything is parsed. It is mounted under `/api/v1` like a
normal route but carries no JWT dependency, so do not confuse "versioned" with
"authenticated".

**Public, by design — no credential of any kind:** the four `/r/` `/p/` share
routes and the three `/api/v1/public/visitor-invitations/{slug}` routes. Their
only secret is the unguessable slug; `/r/{slug}` additionally supports a
password, checked by `POST /r/{slug}/verify-password`.

## Authorization

Two independent axes, both enforced as FastAPI dependencies. `docs/roles.md` has
the full matrix and the exact semantics; the short version:

- `require_role(*roles)` — the caller's `profiles.role` must be in the list.
- `require_scope(name)` — passes when `admin_scope` is **empty** (empty means
  *full* access, not *no* access) or contains `name`.
- `require_dev_admin` — `role == "ADMIN"` **and** `is_dev_admin`. Destructive and
  impersonation routes only.

Both failures are **403** `{"detail": "Insufficient permissions"}` (dev-admin says
`"Dev admin required"`). In the tables below, `ADMIN AGENT` means either role
passes; a trailing `+ documents` means a `require_scope("documents")` also
applies. Where a router-level gate and a route-level gate both apply, the table
shows the intersection — the effective set.

Some endpoints narrow further **inside** the handler: a LANDOWNER reading
documents or interactions is restricted to the properties it holds a grant for
(`backend/app/features/grants/access.py`). Clearing the gate is not the same as
seeing the whole tenant.

## Conventions

`PATCH` for partial updates; there is **no `PUT`** anywhere in the API. `DELETE`
answers **204** with no body and is a soft delete on the 21 tables that carry
`deleted_at` (see `docs/disaster-recovery.md`). Creates answer **201**. Filters are
query params on the list endpoint — there is no `/search` route. `GET` list
endpoints take `limit`/`offset`; the ceiling is per-router (`le=500` on most,
e.g. `properties/router.py:41`) and the `DEFAULT_PAGE_SIZE`/`MAX_PAGE_SIZE`
constants in `constants.py:4-5` are **dead — nothing reads them**.

Errors are FastAPI's default shape, `{"detail": "..."}`, with English messages.
See `docs/api-conventions.md` for the rules that govern new endpoints.

## What is not here

- **No public/BUYER-facing property browsing.** `GET /properties` is gated to
  ADMIN AGENT LANDOWNER CONTENT (`properties/router.py:35`); BUYER gets 403 on
  every route in the API.
- **No `/api/v2`.** Bump only on a breaking change, per `docs/api-conventions.md`.
- **No route outside these tables.** Every gated route is listed above and every
  ungated one is in the public table — the generator asserts it, so an
  unclassified router fails the build of this document rather than disappearing
  from it.
