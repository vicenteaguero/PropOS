# PropOS v0.2.0 — Plan

Written 2026-08-31 from a 24-dimension audit of v0.1.0 at `8b2eb23d` (branch
`dev`), run as two rounds of parallel read-only auditors (9 + 15). Every gap
cites a file or doc; every proposal has a scope (S ≤ 1 day · M ≤ 1 week · L > 1
week) and a priority. The full audit, including the security findings that this
public file only references by id, lives in `docs/audits/v0.1.0-r4/R4-AUDIT.md`
(gitignored on purpose — see `docs/audits/README.md`).

**v0.1.0 in one line:** every spec feature is reachable end-to-end, R3 closed
123/124 findings, two real brokers have been on it since 2026-08-23 — and
nobody is paged when it breaks, the only backup is a two-week-old laptop dump,
and the product is **multi-tenant in its tables and single-tenant in its
identity**: brand, WhatsApp number, sender address, mailbox and active tenant
are process-wide globals, one of them literally the string `ANAIDA`.

**v0.2.0 in one line:** ship multi-tenant first (§3.0 — it is blocking and a
second inmobiliaria is arriving), then make the product safe to depend on
(observability, backups, isolation and auth backstops, retention that actually
runs), make Propo conversational, and give the real users the three domain
things a Chilean brokerage cannot run without — arriendo/venta, real commission
math, UF↔CLP.

> **Read §3.0 before anything else.** Creating the second tenant row today
> breaks the **first** tenant's WhatsApp, and the second tenant cannot be
> created at all because the slug column is a Postgres enum.

### 3.0 MT — Multi-tenant (BLOCKING; ships before everything else)

**Scope change, 2026-08-31.** A second inmobiliaria starts on PropOS. The owner
requires multi-tenant support as a v0.1.0-level obligation, not a v0.2.0
feature. A 12-agent hunt found **120 single-tenant findings, 46 of them
blocking** (deduplicated to MT1–MT24 below; full evidence in the private R4
audit).

The headline: **v0.1.0 is multi-tenant in the data model and single-tenant in
its identity.** 79 tables carry `tenant_id`, 189 RLS policies exist, inbound
WhatsApp already resolves a tenant per receiving number — but the brand, the
phone number, the sender address, the mailbox and the active tenant are all
process-wide globals, and creating the second tenant row **breaks the first
tenant** before the new one sends anything.

Three facts decide the order of everything below:

1. **MT2 is a live regression, not a future risk.** `channels/tenant_routing.py:69`
   falls back to "the only tenant" only when exactly one `tenants` row exists.
   `supabase/seed.sql:4-5` already inserts `anaida` **and** `ceter`, and
   `make seed-demo` adds a third. Verify first — `make query SQL="select id, slug from tenants"` —
   because if that count is already > 1, unmapped inbound WhatsApp is being
   dropped **today** with `TenantRoutingError`.
2. **Inbound is per-tenant, outbound is global.** `tenant_routing.py` resolves
   the tenant from the receiving `phone_number_id`; `kapso/client.py:34` sends
   from `settings.kapso_phone_number_id` regardless of tenant. So tenant #2's
   messages leave on tenant #1's number *and every reply routes back into tenant
   #1's inbox*. This asymmetry is the single largest cross-tenant leak.
3. **A person is structurally single-tenant.** `profiles.tenant_id` is `NOT NULL`
   and `activate_tenant` mutates it globally, while `profiles(LOWER(email))`,
   `profiles(rut)` and `user_phones(phone_e164)` are globally unique. One human
   cannot exist in two agencies, and a dual-membership user has one
   machine-wide current tenant across every device, cron job and RLS check.

## 5. Exit criteria

**Multi-tenant gate (§3.0) — verified with two live tenants before any other exit criterion counts:**

- Creating tenant #2 from the UI succeeds, and tenant #1's inbound WhatsApp keeps working across the insert (`kapso_webhook_events` for tenant #1 grows during and after).
- Tenant #2's WhatsApp prospect is greeted with **tenant #2's** name, from **tenant #2's** number, and the reply lands in **tenant #2's** inbox; the same message never appears in tenant #1's.
- Tenant #2's password reset and reminder e-mails arrive from tenant #2's verified domain; a CRM reply is signed by the thread's own account.
- `rg -ni 'anaida|ceter' backend/app frontend/src config supabase --glob '!*test*'` returns nothing on a code or config path.
- A new tenant opens Agenda with event types, Clientes with a pipeline and its transitions, and `/admin/settings/clientes` with templates, checklists and tags — none of it hand-made.
- The same person (same e-mail, same RUT, same phone) can hold a membership in both tenants, and switching workspaces on one device does not change what the other device sees.
- A tenant ADMIN cannot write another tenant's channel routing through `PATCH /v1/tenants/me`.
- The cross-tenant suite (MT22) runs on every push and fails when a write endpoint, a Storage path, a cache or a WhatsApp direction leaks.
- `docs/tenant-onboarding.md` was followed end to end by someone who did not write it.

**Then the rest.** v0.2.0 is done when all of the following are also true:

## 8. Method

Twenty-four parallel read-only auditors in two rounds. Round 1 (9): spec
carry-over, frontend/mobile, backend quality + security, Propo, ops/DR,
CRM + Finanzas, feature states + IA, git + August audits trajectory, tests/CI.
Round 2 (15): schema + migrations, frontend performance, PWA lifecycle,
auth + session, documents, notifications, e-mail, Client Agent, locale,
imports/export, orphan features, dependencies, frontend code health, tenant
lifecycle, privacy + unit economics. Each returned gaps with `file:line`
evidence and proposals with scope and priority; merged and de-duplicated by
hand, security items moved to the private audit. Two auditors disagreed on the
calendar payment feed — the SQL union (`20240601000070`) settles it as shipped.
Re-verify any row with the cited path before acting on it; the audit read
code, it did not run it.
