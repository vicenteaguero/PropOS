## Multi-tenant blockers (added 2026-08-31)

A second inmobiliaria is onboarding, and multi-tenant support is now a
v0.1.0-level obligation. A 12-agent audit found 120 single-tenant findings, 46
blocking. The full list is `v0.2.0.md` §3.0 (MT1–MT24); the five that make
v0.1.0 single-tenant *today*:

1. **A second tenant cannot be created.** `tenants.slug` is the enum
   `tenant_slug ('anaida','ceter','propos-demo')`, while the API and the UI
   accept a free-form slug — `POST /admin/tenants` 500s.
2. **Creating one breaks the first.** `channels/tenant_routing.py:69` falls back
   to "the only tenant" only while exactly one `tenants` row exists; with two,
   every unmapped inbound WhatsApp raises `TenantRoutingError`. `supabase/seed.sql`
   already inserts two, so verify with
   `make query SQL="select id, slug from tenants"` before assuming this is future tense.
3. **Outbound is global while inbound is per-tenant.** `kapso/client.py:34` sends
   from one `KAPSO_PHONE_NUMBER_ID`, so a second tenant's messages leave on the
   first tenant's number and every reply routes back to the first tenant.
4. **The brand and the sender are constants.** `CLIENT_AGENT_BUSINESS_NAME:
   'ANAIDA'` (both Cloud Run env files) greets every tenant's WhatsApp prospects;
   `resend_from_email` defaults to `no-reply@anaida.cl`; the privacy policy names
   CETER and ANAIDA as the *Responsables del Tratamiento* to whoever reads it.
5. **A person belongs to one tenant.** `profiles.tenant_id` is `NOT NULL` and
   `activate_tenant` mutates it globally; `profiles(LOWER(email))`,
   `profiles(rut)` and `user_phones(phone_e164)` are globally unique.

A new tenant also arrives with **no catalogs** — no event types, pipeline,
checklists, templates or tags — because `POST /admin/tenants` seeds nothing and
the event-type migration used a `CROSS JOIN` over the tenants alive at migration
time.

## Required environment variables (new in v0.1.0)

| Variable | Where | Purpose |
|----------|-------|---------|
| `VITE_VAPID_PUBLIC_KEY` | frontend (Vercel, both projects) | Web-push subscription. Backend already holds the private key. |
| `INTERNAL_JOBS_SECRET` | backend (Cloud Run) | Auth for Cloud Scheduler → `/internal/jobs/*`. |
| `EMAIL_SYNC_ENABLED` | backend | Toggle IMAP email sync. |
| `EMAIL_IMAP_HOST/PORT/USER/PASSWORD` | backend (secrets) | Titan mailbox credentials. |
| `EMAIL_SYNC_TENANT_ID` | backend | Tenant that owns the synced mailbox. |

See `docs/cron-jobs.md` for the Cloud Scheduler setup (reminders + email sync).

## Cron jobs

Two Cloud Scheduler jobs (5-min cadence) hit internal endpoints:
- `run-due-reminders` — push reminders for events/tasks/payments.
- `email-sync` — IMAP poll → portal-lead threading into CRM.

**Neither job exists in the project yet** — the endpoints are live, the schedulers
were never created. A third job (`refresh-analytics`) is still missing its
endpoint, so the CRM/finance materialized views only refresh on a manual button
press. See `docs/cron-jobs.md`.

## Security note

P0 closed a real hole: the conversational agent (`/v1/agent/*`) and proposal
acceptance (`/v1/pending/*`) were callable by **any** authenticated tenant user.
They are now `require_role`-gated. CRM/finance routers are role-gated too.

Still open at v0.1.0 (tracked in the private audit reports, see
`docs/audits/README.md`): CRM/finance routers check the role but not the
per-admin scope; the backend runs as service-role so RLS is not a backstop; and
owner/buyer document access is filtered in Python rather than against
`property_grants`. **Do not load real customer data until these close.**
